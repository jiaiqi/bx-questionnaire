## 1. 产品角度

### 1.1 管理端只有列表，没有结果分析与导出（P0）

**现状证据**

- `src/api` 只有 8 个模块：`config/area`、`daq/activity`、`daq/editor`、`daq/record`、`daq/types`、
  `file/attachment`、`file/upload`、`sso/login`。
- 管理端页面只有「问卷列表」与「设计器」；全仓没有统计、图表、导出相关页面或组件。
- 已有的 `srvdaq_record_reply_select`（每次作答一行）与 `srvdaq_record_reply_merge_select`
  （逐题汇总）足以支撑基础统计。

**影响**：问卷产品的价值链是「设计 → 收集 → 洞察」。当前只完成了前两步，回收来的数据在管理端
不可见，运营只能去平台后台看原始表。

**建议**

1. 新增「结果」页（列表行进入）：
   - 概览：回收份数、完成率、平均分、最近提交时间；
   - 逐题分布：选项计数 / 占比（单选、多选、选项题）、数值题均值与区间、文本题列表；
   - 筛选：时间范围、状态（已完成 / 草稿）、必要时按部门（需登录态与 `user_no`）。
2. 导出：CSV（首选，零依赖）；Excel 可后续用 SheetJS 或后端生成。
3. 注意平台限制：`record_reply_select` **不接受 `order`**、**必须带 `condition`**；
   `record_reply_merge_select` **没有 `activity_no`**，题目维度用 `item_seq`。
4. 不建议在前端拉全量作答做统计；数据量大时用分页 + 服务端聚合，或让平台加统计服务。

**验收**：列表任意一份有回收数据的问卷，能进入结果页看到逐题分布，并导出与页面一致的 CSV。

### 1.2 `item_disp_way`（全部 / 逐个）配置无效（P1）

**现状证据**：全仓 10 处引用均在编辑侧（`EditorActivityForm`、类型、`document.ts`），
作答端 `QuestionnaireRunner` 与页面层不读取该字段。

**建议**：二选一，不要留假开关。

- 实现「逐个」：Runner 一次只渲染一题，上一题/下一题，进度条按题推进；需处理草稿恢复、
  校验定位、退出确认。
- 或从编辑表单移除该选项，并在平台侧说明暂不支持。

**验收**：选「逐个」后作答页一次只显示一题；或该配置项不再出现在 UI。

---

### 1.3 `answer_times`（1 次 / 多次）仅展示（P1）

**现状证据**：Runner 只在卷首展示 `answer_times` 文案；客户端没有重复作答拦截。

**建议**：先向平台确认服务端是否强制。若否，前端在提交前查询本机/账号记录并提示；
最终仍应由服务端校验（前端拦截只能防误操作，不能防绕过）。

**验收**：`1 次` 的问卷在同一账号第二次进入时给出明确提示或只读；`多次` 不受影响。

---

### 1.4 分享链路是半成品（P2）

**现状证据**

- `src/api/daq/record.ts` 有 `recordShareAdd`，但在死代码白名单中，理由写明：
  「H5 分享需要微信 JSSDK，小程序端需新后端服务，均超出接口不变范围」。
- 结果页没有分享/二维码入口（只有重新测试、返回封面）。

**建议**：分端做。

- H5：复制链接 + 生成二维码（本地 canvas/纯 CSS 都可，不引外链）；
- 小程序：`onShareAppMessage` / `onShareTimeline` + 现有 `recordShareAdd` 埋点；
- 分享落地到封面页，带上来源参数，便于统计。

---

### 1.5 模板 / 复制问卷 / 题库（P2）

**现状**：管理端只能「新建空白问卷」；全仓没有复制实现。每份问卷从零搭，运营成本高。

**建议**：优先做「复制问卷」（见 §9 的复制实现，可复用同一套 payload 构造），
再考虑模板库与跨问卷题库。

---

### 1.6 草稿只在本机（P2）

**现状**：本地 `storage` 草稿按 `activity_no` 隔离；服务端逐题草稿存在，但跨设备续答没有
明确入口与提示。

**建议**：记录页对「未完成」记录明确「继续作答」；登录用户进入问卷时优先恢复服务端草稿，
并提示「已恢复上次进度」。

---

### 1.7 敏感数据的知情同意（P2）

健康测评涉及敏感信息。当前隐私说明只是文案，没有同意记录。

**建议**：首次进入健康类问卷时增加一次性同意项（记录文案版本与时间），并在结果页说明数据用途。

## 2. 工程化与 CI

### 2.1 CI 覆盖不足（P0）

**现状**：`.github/workflows/ci.yml` 只做 `build h5` → `type-check` → `lint` → `test`。
以下**不需要网关**的检查没有进 CI：

- `pnpm build mp-weixin --mode test`
- `pnpm check:mp`
- `pnpm check:cond`
- `pnpm scan:dist`

**建议**：新增一个 `artifacts` job（与主 job 并行或串行），跑上述四条；
预计增加 2–3 分钟，但能把「小程序产物、条件编译剥离、票据/网关泄漏」纳入每次 PR。

### 2.2 CI 注释与实际基线漂移（P1）

`ci.yml` 注释曾写「其余 678 项用例」，实际为 783；本轮已校正。建议后续改为从 README 单一引用，
并加一条「测试数与 README 一致」的守卫（类似死代码扫描的思路）。

### 2.3 无覆盖率（P1）

`vitest.config.ts` 没有 coverage 配置与阈值。783 项说明「测了很多」，但不说明「漏了什么」。

**建议**：接入 `@vitest/coverage-v8`，先只统计 `src/domain` 与 `src/composables`（当前核心），
给 80% 行覆盖阈值；`views/components` 单独逐步加，不要一次卡死。

### 2.4 无视觉回归（P1）

V6 刚做完整站改版，CSS 回归目前完全靠人眼截图。

**建议**：Playwright 截图基线，覆盖 6 个关键屏 × PC/移动两档：封面、作答、结果、列表、设计器、
登录。网关可用路由拦截返回固定 fixture（仓库已有 `test/fixtures/raw`），避免依赖内网。

### 2.5 CDP 脚本未进 CI（可接受，但可补夜间）

`smoke/e2e/a11y/editor/special/embed/perf` 都依赖 dev server 与网关/票据。进 GitHub 托管 runner
不现实，建议：

- 自托管 runner（内网可达）跑 nightly；
- 或把网关 mock 后，把 `smoke` + `a11y` 放进 PR。

### 2.6 仓库治理缺口（P2）

- 无 Dependabot / Renovate、无 `pnpm audit`；
- 无 PR 模板 / CODEOWNERS / CHANGELOG / 发布流程；
- `.github` 目录当前只有 `ci.yml`。

### 2.7 版本约束只在 CI（P2）

`package.json` 无 `engines`，仓库无 `.nvmrc` / `.node-version`。CI 固定 Node 22 / pnpm 12.5.1，
本地靠自觉。

> 注意：`packageManager` 字段是**刻意不加**的（避免 pnpm 12 把自身二进制包写进 lockfile，
> 实测 +158 行膨胀）。建议用 `.node-version` + `engines` 或 Volta，不要贸然加 `packageManager`。

状态点、输入框、空态、标签在作答端与管理端各写一份。可抽 `src/styles/patterns.scss`

### 4.3 代码卫生（现状良好）

- `any`：0；`v-html`：0；真实 `TODO`：0（此前命中的是 CSS 类名 `__shackle` 里的 "hack"）；
- `@ts-ignore`：13 处，全部在生成的 `auto-imports.d.ts`，不是源码问题。

### 4.4 请求层（P1）

现状：有超时（默认 20s）、`0011` 明确禁止静默重试、operate 数组体逐项校验；但**没有**：

- 网络错误 / 网关 5xx 的**有界重试与指数退避**（仅对幂等 select 安全）；
- 请求**取消**（页面切走后响应回来覆盖新状态）；
- 并发去重（同一 key 的重复查询）。

建议：在 `utils/request` 增加可选 `retry: { times, backoff }` 与 `AbortSignal` 支持，
默认关闭，查询类接口按需开启。

### 4.5 上传限制（P1）

`BxImageField` 只限制张数（`item_type_attr.fileNum`），未见大小/类型/压缩限制。
移动端大图容易超时或失败。建议：`uni.chooseImage({ sizeType: ['compressed'] })` +
前端大小上限（如 10MB）+ 明确错误文案；服务端也应校验。

### 4.6 全局错误监控（P1）

目前没有 Sentry / 自建上报。H5 白屏、小程序报错只能靠用户反馈。
建议接 app 级 `onError` + 轻量上报（带版本、路由、UA、错误栈），先只上报不阻塞。

## 9. 发布/编辑版本隔离（详细方案）

### 9.1 问题本质

当前保存是**原地 diff 更新**同一份 `activity_no` 下的活动、题目、选项：

- 活动：`srvdaq_activity_cfg_update`
- 题目：`srvdaq_item_cfg_add/update/delete`
- 选项：`srvdaq_option_cfg_add/update/delete`

作答记录只带 `activity_no` + `fill_batch_no`；结果页/记录页展示时按 `activity_no` 读取**当前配置**。
因此只要在「进行中 / 已结束」的问卷上改了题干、选项文案、选项顺序、分值或正确答案，
历史作答的展示与判分口径就会跟着变。这不是显示问题，是数据正确性问题。

平台侧现状（以仓库类型与代码为据）：

- `DaqActivityRow` 没有 version / parent / source 字段；
- `activity_no` / `item_no` / `option_no` 都是 `sysauto` 生成；
- 新增活动时服务端不会自动把 status 派生为「进行中」，status 由调用方显式发。

> 若平台元数据允许新增列，最彻底的是加 `source_activity_no` / `version_no`；
> 在未确认前，方案必须能在「无新列」的前提下成立。

### 9.2 方案对比

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 发布锁 + 复制新版本（推荐先做） | 未开始=草稿可编辑；进行中/已结束只读；改题走「复制为新版本」 | 无新列、无新服务、数据正确性立刻改善 | 版本之间无自动关联；需要改新建默认状态与测试 |
| B. 双活动（草稿 + 发布） | 每份问卷常驻 draft 与 live 两个活动，发布时复制 | 可先改后发、可灰度 | 活动数量翻倍；仍需 copy；列表复杂度高 |
| C. 平台版本列 + 快照 | 新增 `version_no/source_activity_no`，发布时快照题目 | 最完整，可回滚/对比 | 需后端与元数据改造，周期最长 |

**建议路径**：先做 A（1 周内可交付），把「发布后不可改」这条数据约束立住；
B/C 作为后续演进，其中 C 需要平台配合。

### 9.3 方案 A：发布锁 + 复制为新版本

#### 9.3.1 状态语义调整（前置）

| status | 新语义 | 可编辑 | 可被作答 |
| --- | --- | --- | --- |
| 未开始 | 草稿（未发布） | ✅ | ❌（分享/作答入口应拦截） |
| 进行中 | 已发布 | ❌ | ✅ |
| 已结束 | 已归档 | ❌ | ❌ |

**必须改的现有行为**：`emptyActivity()` 当前默认 `status: '进行中'`，这是为了「新建即可答」。
在方案 A 下应改为 `未开始`；发布动作显式置 `进行中`。影响：

- 设计器「保存」与「发布」的语义分离（保存草稿 / 发布上线）；
- 列表状态筛选与空态；
- 现有 `editor:e2e` 直接编辑一份「进行中」的演示问卷，必须改为在草稿上测；
- 平台新增不带 status 时默认就是「未开始」，与服务端语义一致。

#### 9.3.2 设计器锁

- 载入后若 `status !== '未开始'`：进入只读态——隐藏/禁用保存、发布、放弃、所有编辑控件；
- 顶栏状态文案改为「已发布 · 只读」，并展示「复制为新版本」主按钮；
- 只读态仍需保留「预览」与「在新页面打开已保存版本」；
- 前端锁只是体验，**生产环境应同时由平台权限/服务校验兜底**（前端防误操作，不防绕过）。

#### 9.3.3 复制为新版本（核心实现）

入口：设计器顶栏、列表行操作。弹层字段：新标题（默认「原标题（副本）」）、
是否继承时间窗（默认新建时间窗）、是否发布后结束旧版本（默认否）。

执行顺序（无事务，先建父再建子）：

```text
1. activityAdd(activityPayload(src) 去掉身份/派生列, status: '未开始', title: 新标题)
   → newActivityNo
2. itemAdd(src.items.map((it, i) => itemPayload(it, i, newActivityNo)))
   → effect_data[i].item_no（与入参同序）
3. optionAdd(所有题的选项展平：
     optionPayload(option, i, itemNoByClientKey[item.clientKey]))
4. （可选）activityUpdate(oldActivityNo, { status: '已结束' })
5. uni.redirectTo(设计器 ?activity_no=newActivityNo)
```

可以直接复用：

- `activityPayload()` / `itemPayload()` / `optionPayload()`（`src/domain/editor/document.ts`）；
- `activityAdd()` / `itemAdd()` / `optionAdd()` / `activityUpdate()`（`src/api/daq/editor.ts`）；
- 现成的 `planSave` 只适合「原地保存」，复制要单独写一个纯函数
  `buildCopyPayloads(doc, newTitle)`，便于单测。

需要显式处理的字段：

- 不传：`activity_no`、`classify_path`、`classify_name`、`info_collect_type`（服务端派生）、
  任何 `raw` 回读列；
- 重置：`status = '未开始'`、`start_time/end_time` 用新的默认窗口（或继承，由弹层选择）、
  `submit_count` 不传；
- 保留：`classify`、`keyword`、`activity_image`、`perm_type`、`answer_times`、
  `item_disp_way`、`modify_*`、`passing_mark`、`summary`、`start/end_remark`、`submitted_tip`、
  `submit_label`、`act_option`；
- 题目/选项：`item_seq`、`option_seq`、`option_view_no` 由位置重新生成，不复制旧序号；
- 图片/附件：复用 `file_no` 即可，不要重新上传。

#### 9.3.4 失败与并发

平台没有事务，失败可能留下半成品：

- 任一步失败：提示「新版本已部分创建（编号 X），可重试或清理」；
- 清理顺序：先 `optionDelete`（已创建的选项）→ `itemDelete`（已创建的题目）→
  `activityDelete(newNo)`；若平台对活动删除有级联，仍按显式顺序执行，避免「赌级联」；
- 复制按钮要做**单次在途锁**（saving 状态 + 禁用），避免双击产生两份副本；
- 复制失败后可重试；重试前先判断活动是否已创建，避免重复建活动。

#### 9.3.5 版本关系与命名（无新列时的取舍）

- 不做自动版本号。标题由用户确认，默认「原标题（副本）」；
- 如需「同一问卷的多个版本」在列表聚合，需要平台加 `source_activity_no`；
  在此之前不要用 `keyword`/`remark` 塞机器标记（会被搜索与展示污染）；
- 可选过渡：复制成功后提示「旧版本编号 X 已结束」，并在两端列表展示同一分类，便于人工对照。

#### 9.3.6 发布切换

- 「发布」= 保存草稿 + `activityUpdate(status: '进行中')`；
- 若是从某个已发布版本复制而来，发布新版本时可选择「结束旧版本」：
  先让新版本进入「进行中」，再结束旧版本；第二步失败时提示「旧版本仍在线，请手动结束」，
  避免出现「旧已结束、新未上线」的空窗。

#### 9.3.7 测试与验收

**单元测试**

- `buildCopyPayloads`：身份/派生列被剔除；status 重置；题目/选项序号重排；
  图片与引用配置保留；空题/空选项不出错；
- 状态矩阵：未开始可编辑、进行中/已结束只读；发布动作只从草稿发起。

**e2e（新增）**

1. 新建草稿 → 加题 → 保存 → 发布 → 进入只读；
2. 只读态点「复制为新版本」→ 新草稿可编辑 → 发布 → 旧版本变「已结束」；
3. 旧版本的历史结果仍能打开，题目文案与提交时一致（因为未被修改）；
4. 复制过程中断（mock 失败）→ 有明确错误与清理路径。

**现有脚本影响**

- `editor:e2e` 目前编辑「进行中」的演示问卷，需改为「先复制/新建草稿再改」；
- `smoke` 的设计器页在已发布问卷下应显示只读态，需更新关键文本断言（如「已保存」→「已发布」）。

#### 9.3.8 迁移与发布节奏

1. **先上只读锁**（不改默认状态也可以先对「进行中/已结束」只读）；
   给运营一份「需要改题请复制新版本」的说明，避免突然无法编辑；
2. 再把 `emptyActivity` 默认改为「未开始」，上线「保存草稿 / 发布」两段式；
3. 最后做「发布时结束旧版本」的一键切换；
4. 全程保持 `activity_no` 不变的前提下不修改已发布配置——这是数据正确性的底线。

#### 9.3.9 若平台可加列的升级路径（方案 C）

向平台确认 `bxdaq_activity_cfg` 是否可扩展列（低代码平台通常有元数据扩展能力）：

- 加 `source_activity_no`（复制自哪份）与 `version_no`（整数）；
- 列表按 `source_activity_no` 聚合版本，展示「v3 · 进行中」；
- 结果页可按版本对比；
- 此时方案 A 的复制流程不变，只是多写两个字段，UI 可做版本历史与回滚。
