**平台会话 cookie 导致的权限差异（第三例）**

同一服务、同一票据，Node 直连成功而浏览器端失败，已累计三例：

| 服务 | 浏览器端表现 | Node 直连 |
| --- | --- | --- |
| `srvdaq_init_view_select`（`type=use`） | 非活动创建人，无法查看其它用户填写信息 | 成功返回 `user_data` |
| `srvdaq_record_reply_merge_select` | 需要登录访问（0011） | 成功 |
| `srvdaq_item_cfg_select` | 无权限访问（0011） | 成功返回 41 行 |

原因是平台按**会话 cookie 的用户身份**鉴权，会覆盖票据身份；Node 无 cookie，
只按票据鉴权。真实用户在自己浏览器里用自己的登录态访问是正常的 ——
这是平台鉴权设计，不是代码缺陷。

| 组件 | 交互结果 |

**修掉一处真问题**：`datetime` 退化成只能选日期。老工程把 `dateType` 直接当作低代码
表单组件的 type（`date`/`time`/`datetime`），由组件库处理三种模式；新工程改用
uni 原生 `<picker>`，而它**没有 datetime 模式**，原来的 `mode` 计算把 `datetime`
也映射成 `date`，用户无法选择时间。改为「日期 + 时间」两个 picker 组合。

**框架限制**：uni 的日期 picker 默认从 **1876 年**开始，选生日要滚很久。
已显式传 `start=1900-01-01`/`end=2100-12-31`，但该属性在 **H5 端未生效**
（年份列仍从 1876 开始），属 uni H5 的实现限制，小程序端预期生效，属性予以保留。

> 验证方法备注：判断哪个 picker 弹层展开时，**不能用 `display !== none`** ——
> uni 会把所有 picker 的容器都留在 DOM 里，三个容器都判定为「可见」，
> 结果点错了确认按钮（日期题写入了 `15:59`）。正确标识是
> `.uni-picker-custom.uni-picker-toggle`。

**结果页的服务端作答语义**（CDP 真实浏览器 + 真实网关）

伪造三个服务的响应验证结果页完整渲染时，确认了 `svalue` 的真实形态并修掉三处问题：

`srvdaq_record_reply_merge_select` 的 `svalue` 对选项题返回的是**选项序号**
（`option_view_no`，实测单选返回 `"1"`、`"2"`），不是选项文案：

| 题型 | 真实 `svalue` |
| --- | --- |
| 单选 | `"1"` / `"2"` |
| 多选 | `"2"` / `"3"`（**只返回一个值**） |
| 文本 | 作答原文 |
| 数字 | `"2026.00000"`（带小数尾巴） |

三处修复：

1. **「我的作答」显示序号**：直接渲染会让用户看到「我的作答：1」。
   新增 `describeServerValue` 还原为选项文案，兼容序号 / `option_no` / 文案三种形态，
   匹配不上时保留原值便于排查；数字题去掉小数尾巴。
2. **统计与逐题作答数据源不一致**：统计用本地回填（`init_view_select` 的 `user_data`），
   逐题用服务端 merge。当 `type=use` 失败但 merge 成功时（如已登录但非活动创建人），
   会出现「逐题显示有作答、统计却全是 0」。新增 `serverAnswersToAnswerMap` 统一以服务端为准。
3. **纯空白作答值被当成有作答**：原来的空串长度检查挡不住 `"   "`，会让没答的题算成答错。

浏览器回归：选项题显示「选项甲」而非「1」，多选显示「多选甲、多选乙」，
统计由 `0 答对/0 答错/2 未答` 变为 `2 答对/0 答错/0 未答`，无 JS 异常。

**统计口径**：`calcScore` 会跳过**没有配置正确答案**的题（文本题等），
它们不计入总分、也不计入「未答」。因此「2 答对 / 0 未答」里的分母只是客观题，
不是全部题目 —— 这是评分语义，不是统计遗漏。

全部属于**静默失效**：页面正常渲染、测试全绿，只有真实数据或截图才能发现。

**根因与对策**：第 1–9 处源于"凭接口名推测契约"，第 10 处源于"只读了数据产生点、没看下游消费点"，第 11 处源于"把平台的宽容当成支持"。对策固定为：**先读老工程源码，再用实测验证**；实测能证明"会不会炸"，但**语义正确性只能靠源码**（第 8 处即"实测通过但依据不足、仍予删除"）。

## 五、平台行为实测：静默失效清单

这类问题的共同点是**请求不报错、页面正常渲染**，只有真实数据才能发现。集中记录，避免重犯。

| 服务 | 参数 | 实际行为 | 本工程做法 |
| --- | --- | --- | --- |
| `srvdaq_record_reply_select` | `order` | 传任何排序字段（`start_time`/`end_time`/`id`/`create_time`，asc 或 desc）都**返回 0 条且不报错** | 默认不传，显式要求时才带 |
| `srvdaq_record_reply_merge_select` | `order` | 传 `order` 直接 **FAILURE** | 不传 |
| `srvdaq_record_reply_merge_select` | `condition: activity_no` | 报 `CONDITION_COLUMS_NOT_EXISTS`（服务列里没有 `activity_no`） | 只传 `fill_batch_no` |
| `srvdaq_init_view_select` | `order` | **非必需**：带 `item_seq asc` 与不带都返回同样条数 | 带上（无害，且与老工程一致） |
| `srvdaq_activity_sug_select` | `condition: activity_no` | 必需；测试活动无建议数据时返回 0 条且 SUCCESS | 传 `activity_no` + 可选 `fill_batch_no` |
| `srvdaq_record_reply_select` | `condition: []` | 直接 **FAILURE** | 始终至少给一个条件 |
| `srvfile_attachment_select` | `condition: []` | 正常返回（实测 3 条） | 按 `file_no eq` 查询 |
| `srvconfig_area_adj_select` | `condition: []` | SUCCESS 但 0 条（**测试环境该表无数据**） | 顶层不传 `parent_no` |
| 写操作 | — | `result_submit` 返回的 `fill_batch_no` 在 `response[0].response`；草稿保存第二次起 `response` 为 `null` | 按此解析 |

另外注意**写入后立即查询存在可见性延迟**：提交成功后马上按 `activity_no` 查会返回 0 条，数秒后再查才出现。结果页因此不能假定"提交完就能立刻读到服务端得分"，本地兜底是必要的。

**关键结论：同一个参数在不同服务上的表现并不一致。**

| 参数 | 服务 A 的行为 | 服务 B 的行为 |
| --- | --- | --- |
| `order` | `record_reply_select`：静默返回 0 条 | `record_reply_merge_select`：直接 FAILURE |
| `condition: []` | `record_reply_select`：直接 FAILURE | `srvfile_attachment_select`：正常返回 |
| `order` | `init_view_select`：非必需（带不带一样） | `record_reply_select`：带就废 |

所以**不能从一个服务的行为推断另一个，必须逐个实测**。这条已经三次被验证。

**同类教训（已第二次遇到）**：契约测试如果只断言「当前实现长什么样」，会把错误行为一起锁进测试，让它看起来「有覆盖、很安全」。

- 第 42 轮：测试锁住了 `record_reply_select` 的错误默认排序，改对之后测试反而失败；
- 第 46 轮：测试锁住了 `record_share_add` 的 `share_type: '朋友圈'` 默认值 —— 分享给好友会被静默记成朋友圈，渠道数据失真。

两处都已改为断言正确行为。**写契约测试时先问一句：这个默认值是「后端契约要求」，还是「我顺手写的」？**

### 页面参数与 URL 约定

所有页面统一用 `src/utils/query.ts` 的 `readQuery()` 读取参数 —— 它做安全解码，
遇到含裸 `%` 的值（如活动标题「完成率 100%」）会回退原值，而不是抛 `URIError` 打白屏。
此前 9 个页面各写一套，两个 history 页对 `title` 裸调 `decodeURIComponent` 且无任何保护。

| 参数 | 消费方 | 说明 |
| --- | --- | --- |
| `activity_no` | 全部业务页 | 系统生成，纯数字，解码幂等 |
| `fill_batch_no` | 答题 / 结果 / 记录页 | 32 位十六进制 UUID，解码幂等 |
| `formType` | 答题页 | `form` / `detail` / `view`，纯英文 |
| `title` | 两个 history 页 | **外部入口传入，可能含中文，必须解码** |
| `status` | **无** | 老工程遗留的**死参数**：全工程无任何读取点 |

`status` 目前仍被 4 处跳转拼接（`RecordList`、`cover`、`submitInfo`、`couple`），
其中 `index/index.vue` 的分享路径 `status=进行中` 与老工程一致、已对外发布，故保留不改。
**它的值含中文且未编码**，将来若有页面要读它需一并处理编码，否则小程序端可能解析异常
—— 这也是「保留但记录」而非「直接删除」的原因。

## 六、已知限制

### 1. 结果页无法判断对错（需平台侧处理）

`record_reply_merge_select` 在 parkDev 只返回 `item_type`/`item_seq`/`item_title`/`svalue`/`fill_batch_no`，而老工程依赖以下字段判对错，**当前环境均未返回**：

| 字段 | 用途 |
| --- | --- |
| `option_data[].answer` | `answer === '是'` 即正确答案 |
| `points` | 该题分值 |
| `result` | `'正确'`/`'错误'` |
| `score` | 该题得分 |

**影响**：结果页只能显示"我的作答"与"正确答案"，**不能显示答对/答错统计与逐题得分**。前端无法补偿，需平台侧补齐该服务的服务列。

**补充（浏览器端实测）**：该服务在浏览器端还会因缺会话直接返回 `0011`（见限制 3），
所以「我的作答」在当前环境**拿不到任何服务端作答值**。`svalue` 经实测确认是**用户作答值**而非正确答案
（两条记录对比：一条有 `"1"` / `"2026.00000"`，另一条全为 `null`），故不可拿它当「正确答案」展示；
「正确答案」目前来自题目配置的 `option.isAnswer`。

### 2. 图片上传（需平台侧开通权限）

`srvfile_attachment_add` / `srvfile_attachment_upload` / `srvfile_upload` 在 `file` 应用下均返回「无权限访问」。**老工程也没有上传功能**，故当前只实现只读显示（`BxImageField`）。

### 3. 网关鉴权的两个层次（浏览器端实测）

用 Chrome DevTools Protocol 抓真实请求确认：同一页面、同一票据下，两个服务表现**完全相反**。

| 服务 | 浏览器端结果 | 要求 |
| --- | --- | --- |
| `srvdaq_record_reply_select` | **成功**，返回记录（含 `score` / `state`） | **平台会话 cookie** |
| `srvdaq_record_reply_merge_select` | **`0011` 需要登录访问** | **用户登录态** |

关键在请求层的 `withCredentials: true` —— 浏览器会自动带上平台会话 cookie，
所以**浏览器端记录列表与结果页得分都能正常取到**。

两个反例佐证了这个区分：

- 用 Node 脚本**直连**网关（不带 cookie），即便票据有效，`init_view_select` 与
  `record_reply_select` 也一律返回「无权限访问」；同一票据在浏览器里却成功。
  **说明卡的是会话 cookie，不是票据。**
- `record_reply_merge_select` 返回的是 `0011`（需登录）而非「无权限访问」，
  说明它还要**再高一层**的用户登录态，匿名用户拿不到。

因此旧说法「本地跨域导致记录类服务不可用」**不成立**；准确说法是
**鉴权分两层，浏览器端满足第一层、不满足第二层**。
这也是「同一服务/参数在不同条件下表现不一致」的**第 4、5 次**实证。

页面据此区分两种状态：服务端明确返回「无作答」时显示「未作答」，
请求失败时显示「暂无法获取」，**不把「数据不可用」谎报成「未作答」**。

**关键推论（影响业务，非仅本地）**：该活动的 `perm_type` 是「匿名访问」，而 merge 需要登录态。
也就是说**匿名作答的用户在任何环境下都拿不到逐题作答值**，不只是本地开发受限 ——
这是平台侧的权限设计，前端无法绕开。刚提交完的当次结果页仍可用本地回填值正常显示作答。
此点已列入「待业务确认」。

### 4. favicon 在子路径部署时取不到（仅影响图标）

uni-app 生成的 `<link rel="icon" href="static/logo.svg">` 不带子路径前缀，设置 `h5.favicon` 无法改变该行为。仅影响标签页图标，不影响功能；如需修复可在部署侧补 `/static/logo.svg` 反向代理。

### 5. 草稿保存会在服务端逐条新建记录（老工程同样如此）

实测（浏览器抓包 + 记录查询）：`srvdaq_activity_result_save` **每次调用都会新建一条记录**，
即便请求里带了 `fill_batch_no`，响应仍回传一个**新的**批次号，传入值不被当作复用键。

因此逐题即时保存会在服务端留下多条「未完成」草稿。**老工程行为完全相同**
（`indexyax.vue` 也逐题保存、也传批次号），不是本工程引入的问题；
在「后端接口不变」的约束下前端无法消除，故不处理，仅记录。

前端能做且已做的是**不让批次号漂移**：只在首次保存锁定批次号，之后忽略响应回传的新值
（对齐老工程 `if (data.fill_batch_no && !self.fill_batch_no)`）。
否则同一次作答会被割裂到多条草稿，提交只能挂到最后一条上，其余成为孤儿记录。

**本地草稿续答**：服务端草稿是「逐题一条记录」且需要网络，因此答题页额外在本地
（`bxq:draft_answers:<activity_no>`，按活动隔离）同步一份答案快照，刷新或闪退后可直接恢复。
这条路径不依赖权限，匿名用户同样可用 —— 而服务端 `user_data` 回填受权限约束（见限制 3）。

续答与作废的完整语义（均已端到端实测）：

| 场景 | 行为 |
| --- | --- |
| 作答后刷新页面 | 答案与批次号都恢复，继续在同一批次上作答 |
| 提交成功后 | 批次号与本地草稿一并清空，下次进入是新作答 |
| 提交前离开再进入 | 保留草稿，属于续答 |

注：老工程用 `beforeDestroy` 在离开答题页时清空批次号，但**实测 uni-app H5 端该钩子不触发**
（页面由 uni 路由栈管理），小程序端却会触发 —— 依赖它会造成两端行为不一致，故未采用。
改由「提交成功后清除」覆盖真正需要防脏的场景；这也顺带修掉了老工程的一个缺陷：
它 H5 端提交后 `fill_batch_no` 残留，再次进入会把新作答写进已完成的那条记录。
