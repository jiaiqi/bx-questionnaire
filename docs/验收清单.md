**界面级保存链路（`pnpm editor:e2e`，2026-10-11 实测通过）**：

```
服务端当前标题："员工满意度调查（演示问卷）"（SUCCESS）
  ✓ 设计器加载出已有问卷（标题栏为「问卷设计」而非「新建问卷」）
  ✓ 页面上没有「放弃」按钮（刚载入不算有改动）
  ✓ 等到已载入（标题输入框有值）—— "员工满意度调查（演示问卷）"
  ✓ 标题已写入输入框 —— "员工满意度调查（演示问卷）·UI联调"
  ✓ 改完之后出现「放弃」按钮（dirty 生效）
  ✓ 点到「保存」按钮
  ✓ 保存给出反馈 —— 「放弃」消失
服务端保存后标题："员工满意度调查（演示问卷）·UI联调"
  ✓ 服务端标题确实变了
  ✓ 已还原原标题
```

为什么单独要这条：接口层验证只证明「请求发对了」，证明不了**表单到请求体的映射**、
**保存按钮有没有接线**、**dirty 有没有置位**。这条脚本走的是真实浏览器 + 真实后端，
并独立用 `srvdaq_activity_cfg_select` 查回来确认，而不是只看页面提示。

**踩到的坑（值得记下）**：脚本第一版用「文本里含『题目』和『保存』」判断加载完成，
结果**新建态**的壳同样含这两个词，于是立刻通过、拿到一张空表单，还差点被当成「保存失败」。
改成等**标题输入框有值**才是真正的「已载入」。

**编辑器不发送服务端派生字段**：活动的 `classify_name` / `classify_path` / `info_collect_type`，
题目的 `classify` / `classify_path` / `classify_name`；`activity_no` / `item_no` / `option_no` 由服务端生成。
`status` 由调用方全权控制（服务端不会自动改成「进行中」），所以新增与更新都**显式传** `status`。

### 功能对等审计：机械扫描找出的入口缺口

人工比对会漏，所以做了一次机械扫描：把老工程 11 个 `.vue` 的**用户可见中文串**全部提取出来
（去掉 `<style>` 段，371 条），逐条在新工程里找。UI 完全重构下文案本就不该逐字复现，
所以扫描的价值不在「文案是否相同」，而在**逼出「页面存在但没有入口」这类缺口** ——
文案对不上会引我去查对应能力，而能力缺口不会自己冒出来。

据此查出并修复：

- **「答题记录」入口缺失**：老工程标题栏常驻该按钮（无 `v-if`），新工程三个记录页只能靠手改 URL 进入。已在答题页导航栏右侧补「记录」入口（另补键盘可达）。
- **「查看评估结果」入口缺失**：老工程在 `detail` + `info_collect_type==='评估'` 时显示按钮，且**提交成功后评估类活动直接跳报告页**。新工程提交后统一进结果页，若不给入口，评估类活动的建议报告**彻底无法到达** —— 属功能缺失。已在结果页补该入口。
- **导航栏返回兜底丢参数**：页面栈只有 1 层时（从分享链接 / 扫码直接打开）`BxNavBar` 会 `reLaunch` 到封面页却**不带 `activity_no`**，用户落到「缺少活动编号」错误页。与结果页「返回问卷首页」是同一缺陷类 —— 修完一个实例后扫描同类才发现的。
- **问卷地址集中到 `routes.ts`**：地址此前散在 8 个文件里手写，漏参数就是上述缺陷的温床。集中后参数由函数签名强制，并加了**结构性守卫**（单测扫描 `src`，禁止在别处手写带参数地址或写字面地址；反向验证：注入一处手写 URL 立刻变红）。

**确认不是缺口的**（老工程里本就是死代码或入口页）：

| 老工程写法 | 结论 |
| --- | --- |
| `toFeedback()` 硬编码活动号跳意见反馈 | 定义处之外**零引用** → 死代码，不复刻 |
| `toContcat()` 反馈联系方式 | `assessmentResult` 里被注释掉、`survey/result` 里只定义不引用 → 死代码 |
| `submitInfo.vue` 登记信息页 | 老工程**没有任何地方导航到它**（它自己带 `submitInfo` 参数跳去答题页）→ 入口页，靠链接打开，无缺口 |
| `srvwx_basic_user_info_select` | `wxUserInfo` 只写不读，取值处零命中 → 死代码 |
| `couple.vue`（我的测评） | 老工程里**同样没有任何地方导航到它**，也不在 tabBar（是普通页面，靠宿主应用链接打开）→ 入口页，无缺口 |

### iframe 嵌入通信（平台 iframe-embed 契约）

问卷会被外部系统（OA、门户、其它低代码平台）用 iframe 嵌入，子页需要主动告知父页面状态。

老工程的实现是**两套各写各的**：`submitInfo.vue` 发 `set_title` + `h5_loaded`，
`survey/result.vue` 发 `{type:'height', value: scrollHeight}` —— 类型名都不在平台契约里，
且 `assessmentResult.vue` 漏了高度同步。新工程按契约统一实现：

| type | 触发时机 | data | 状态 |
| --- | --- | --- | --- |
| `FORM_READY` | 问卷配置加载完成 | `{serviceName: 'srvdaq_init_view_select'}` | ✅ 实测到达 |
| `ADD_SUCCESS` | 提交成功（问卷提交是新增一条作答记录） | `{action:'add', serviceName, id, effectData, response}` | ✅ 实测到达 |
| `RESIZE` | 内容高度变化 | `{height}` | ✅ 实测到达 |
| `TICKET_EXPIRED` | 收到 `0011` 会话过期 | — | ✅ 实测到达（票据真过期时） |
| `UPDATE_SUCCESS` / `DELETE_SUCCESS` | 更新 / 删除成功 | 同 `ADD_SUCCESS` | 本项目无对应写操作，未触发 |
| `CLOSE_DIALOG` / `REFRESH_LIST` | 业务要求关弹窗 / 刷列表 | 可选 | 由父页面按 `ADD_SUCCESS` 自行决定，子页不替父页面做决定 |

实现要点：

- **嵌入检测**用 `window.self !== window.top`，且**跨域访问 `window.top` 抛 SecurityError 时也算嵌入** —— 跨域 iframe 恰恰是典型嵌入场景，把报错当成「不是嵌入」正好判断反了。
- **`id` 取值优先级**对齐平台 `buildSubmitPayload`：`response.ids[0]` > `response.effect_data[0].id` > 批次号兜底。问卷提交走 `srvdaq_activity_result_submit`，平台把回填字段放在 `response.response[0].response`（实测是 `fill_batch_no`），既无 `ids` 也无 `effect_data`，所以必须有兜底。
- **`RESIZE` 用模块级单例**：uni-app H5 的页面销毁时机与 `onUnmounted` 不完全对齐，只靠组件卸载 `disconnect` 会累积观察者。
- **只在 H5 生效**：`#ifdef H5` 整段剥离，`pnpm check:cond` 校验 3 个新指纹在 H5 产物中存在、在小程序产物中为零（反向验证：去掉 `#ifdef` 后立刻报「#ifdef 未生效」）。

**为什么必须跨域真嵌一次才算验证过**：`postMessage` 是**静默失败**的 —— 父页面没监听、`targetOrigin` 不匹配、上下文拿错，全都表现为「什么都没发生」。所以加了常驻脚本 `pnpm embed [base] [--submit]`：起一个真实跨域父页面把开发服务器嵌进去，收集消息并断言。默认不提交（提交会产生真实记录）。

**跳过的检查必须是响亮的**。记录页那组检查（点「未完成」走续答、点「完成」走查看）原先
「找不到对应记录就静默略过」—— 而**每次跑 e2e 的「暂存草稿」都会新增一条「未完成」记录**，

现在改为先滚动触发加载更多，实在找不到就把「前提不成立」本身记成一条**失败**检查
（反向验证：禁用滚动加载 → 立刻 1 项失败）。

此前的冒烟只验证「页面能渲染」，没验证过任何一次真实交互。`scripts/e2e.mjs`
（`pnpm e2e`）用 CDP 派发真实事件走完整流程，并全程用 `Network.enable` 抓请求作为铁证：

| 检查 | 证据 |
| --- | --- |
| 初始进度为 0 | 「已答 0」 |
| 单选 / 多选 / 文本 / 数字 各 +1 | 进度依次 1→2→3→4 |

**写请求体断言**（默认跑也执行，无需 `--submit`）

此前 e2e 只断言「发出了写请求」，不看请求体内容 —— 序列化被改坏也不会有任何测试
报警。现捕获 `Network.requestWillBeSent` 的 `postData` 并直接断言结构：

| 断言 | 说明 |
| --- | --- |
| 草稿体包含多选题 | 默认跑 |
| 草稿体多选题带 2 个 option_no | 默认跑，多选多值未被截断 |
| 草稿体四题齐全 | 默认跑 |

| 提交体多选题带 2 个 option_data | `--submit` |
| 提交体 option_flag 与 option_data 数量一致 | `--submit` |
| 提交体携带 fill_batch_no | `--submit`，复用草稿批次而非新建 |

**查清悬案：多选只存第一个值是平台限制，不是前端缺陷**

真实请求体证据链：

    前端提交体：option_data=["1","2"]  option_flag=["A","B"]   <- 2 个值
    服务端 merge_select：svalue="3"                            <- 1 个值
    服务端 user_data：option_data=["3"]                        <- 1 个值

前端序列化（`serializer.ts` 的 `OPTION_WIDGETS` 分支）完全正确，两个独立服务都只
保留第一个值。属平台侧多选存储缺陷，在「后端接口不变」约束下前端无法修复，
只能如实记录：**详情模式回填多选题时只会显示一个选中项**。

**脚本修正**：同一逻辑写请求会发出两次，其中只有一个带 `postData`。最初用
`find()` 取第一个，拿到的是没有请求体的那个，导致 4 项断言全假失败。改为挑

### 开发环境票据被空值覆盖（已修复）

`.env.development` 里写了 `VITE_BX_TICKET=`（空值），本意是「票据不要写在本文件里」，
但 Vite 的加载优先级是

    .env.[mode].local > .env.[mode] > .env.local > .env

所以 `.env.development` 里的**空值覆盖了** `.env.local` 里的真实票据，
导致开发环境下所有请求都不带 `bx_auth_ticket`。

**为什么长期没被发现**：按 `activity_no` 查询的接口匿名也有数据，所以此前所有 e2e
都是绿的；只有按 `user_no` 查询的接口才会暴露 —— 匿名查询返回 0 行而**不报错**，
页面显示「暂无记录」，与「真的没有记录」完全无法区分。

**实测证据**（同一服务、条件 user_no=jq + state=完成）：

    无票据          -> 0 行
    带票据          -> 11 行
    带票据+Origin   -> 11 行
    无票据+Origin   -> 0 行

唯一变量是票据。修复前浏览器请求的认证头为空数组 `[]`，修复后为
`["bx_auth_ticket=…", "bx-auth-ticket=…"]`。

**影响面**：`couple` 在开发环境下永远显示空列表；生产环境没有这个空值，不受影响。

**反向验证**：把空值放回去并重启 dev server，e2e 立即变红（认证头 `[]`、卡片数 0、
5 项失败）；移除后恢复全绿。

- src 下不得使用 rpx（扫描 .vue/.scss/.css/.ts，排除注释行）
- tokens.scss 必须定义 `--bx-content-width`（px）

      封面页  116ms   作答页  133ms   记录页  134ms   我的测评  135ms

**内容校验（关键）**：每个页面给一个 `expect` 关键词，对不上判失败并退出码 1。
上一轮踩的坑正是缺这个 —— 默认 production 模式构建时网关指向 gxqcxkj.com，测试

**错误页也有文字**，于是 2742ms 那个假数字被当成了「作答页首屏很慢」。

**反向验证**：把记录页期望词改成不存在的字符串 → 3 个视口全部报错、退出码 1；
恢复后 12 个渲染 0 失败、退出码 0。

**测量前提（缺一个数字就没意义）**

1. 必须测 **dist 产物**：dev server 不压缩、不 tree-shaking、模块按需编译。
2. 必须用 **`--mode test`** 构建：生产构建的网关指向 gxqcxkj.com，测试活动在那边
   不存在，页面显示「活动编号不存在」，测出来的数字是错误页。
3. 不能只判「页面有文字」：错误页也有文字。每个页面都要给关键词做内容校验。

**排查中排掉两个测量错误**

- 首轮用默认 production 模式构建，测的是生产网关；更早一轮的 2742ms「作答页首屏」
  其实是 storage 里活动快照的缓存命中掩盖了请求失败。
- 「同一服务发了两次」是误报：CDP 对同一个请求发两个 `requestWillBeSent` 事件，
  只有其中一个带 `postData`，不过滤就会看成重复请求（那个「请求」耗时 1ms，因为
  它没有 body）。实际只有一个真实请求。

**导出审计**：src 下 60 个值导出中只有 `recordShareAdd` 无引用点，且是有意保留的
（老工程同样没调用）。首轮脚本排除同文件引用导致误报，修正后干净。

**服务端不按调用者身份过滤数据**（2 项集成测试）

修掉票据缺陷后，开发环境的请求才真正带上 `bx_auth_ticket`（此前一直是匿名），
所以必须确认服务端会不会按票据里的身份二次过滤数据。实测逐项对比：

    按 activity_no              带票据 100 行 / 86 个 user_no
                                无票据 100 行 / 86 个 user_no   ← 完全一致
    按 activity_no + state=完成 带票据  24 行
                                无票据  24 行                   ← 完全一致
    不带任何条件                带票据  50 行
                                无票据  50 行                   ← 完全一致
    按 user_no=jq               带票据  28 行
                                无票据   0 行                   ← 静默为空
    按 user_no=<匿名 hex>       带票据   1 行
                                无票据   0 行                   ← 静默为空

**结论**：服务端**不按调用者身份过滤数据**，但 `user_no` 条件在**无票据时被静默忽略**
（返回 0 行而**不报错**）。

**两个直接后果**

1. `history` 页按 activity_no 查询，**匿名也能看到该活动的全部记录** —— 前端不能指望
   服务端做数据隔离，展示层要自己控制。这是平台侧行为，在前端改不了。
2. `couple` 页按 user_no 查询，**必须带票据**；票据缺失时显示「暂无记录」，与
   「真的没有记录」无法区分 —— 这正是票据缺陷藏很久的原因。

**前端补的归属门槛（限制 12）**

后果 1 不只是「多看到几行」：记录卡片点进去会带上 `fill_batch_no`，
`init_view_select` 的 `type=use` 会**如实返回该批次的 `user_data`** ——
也就是**能看到别人的作答内容**。所以记录页加了归属过滤：

| 状态 | 归属判定依据 |
| --- | --- |
| 已登录 | `row.user_no === login_user_info.user_no`（服务端也带条件，前端再判一次兜底） |
| 未登录 | `row.fill_batch_no` 在**本机产生过的批次号**里（新 key `bxq:my_batches`，只记批次号不记答案） |

为什么未登录时只能靠本机记录：匿名提交每次都生成新的 32 位随机 `user_no`，
同一台设备的历史归不到一起；而按 `user_no` 查询要求**调用者的平台会话**，
前端没有第二个身份来源。所以这是**体验层门槛，不是安全边界** ——
真正挡住越权读取必须由平台按调用者身份过滤（待办）。

页面会如实告知：「未登录，仅显示本机作答记录（已隐藏 N 条其他账号的记录）」。
把隐藏条数写出来是刻意的 ——「不是没有记录，是不给你看别人的」和「一条都没有」
是完全不同的两件事。

**实测**：未登录时本机 1 条记录 → 渲染 1 条、隐藏 19 条；加 `--submit` 后
本机 2 条（1 完成 + 1 未完成）→ 渲染 2 条、隐藏 18 条。

**反向验证踩到的坑（两条检查本身无效）**：最初写的是「卡片数 ≤ 20」和
「提示条文案存在」。变异测试（把 `visibleRows` 改回不过滤）证明两条都**无效**：
卡片数正好 20，卡在边界上通过；而提示条的隐藏数是按**未过滤**的 `rows` 算的，
过滤与否都会出现。改成断言不变式 —— **渲染出的每条记录，批次号都必须在本机记录里**
（不过滤则他人批次号出现 → 立刻变红），再加 `cards <= mine.length` 防「过滤过头
把自己也滤没」。同时踩到：e2e 里必须用 `uni.getStorageSync` 读，
裸 `localStorage.getItem` 拿到的是 uni-app 加了类型包装的值。

**反向验证**：把「无票据应返回 0 行」改成预期 999 → 变红（`expected +0 to be 999`）；
恢复后 7 项全绿。

**更正旧记录**：此前记「record_reply_select 加 user_no 返回 0 行，说明不支持按用户
过滤」。真正原因是**无票据**，与 user_no 条件无关 —— 带票据时该条件完全生效。

**环境变量配置的回归防护**（5 项单测）

起因：`.env.development` 里写过 `VITE_BX_TICKET=`（空值），本意是「票据不要写在本文件里」，
但 Vite 的加载优先级是

    .env.[mode].local > .env.[mode] > .env.local > .env

所以那个空值**覆盖**了 `.env.local` 里的真实票据，开发环境所有请求都不带
`bx_auth_ticket`。而且它**不报错** —— 按 activity_no 查询的接口匿名也有数据，
只有按 user_no 查询的接口会静默返回 0 行，与「真的没有记录」无法区分。

反过来，`.env.production` 里的空值**是刻意的**：生产构建同样会加载 `.env.local`，
正是这个空值把联调票据挡住，它才不会被打进产物。

两条规则方向相反，靠人记不住，所以固化成单测：

- `.env.development` / `.env.test` 不得定义 `VITE_BX_TICKET`
- `.env.production` 必须保留**空的** `VITE_BX_TICKET`
- `.env.local` 存在时票据不得为空
- 三个环境的 `VITE_BX_GATEWAY` 都必须非空

**反向验证**：往 `.env.development` 加回空票据 → 测试变红；删掉 `.env.production`
的空票据 → 测试变红；恢复后 5 项全绿。两条方向相反的规则都被真正守住。

**探测记录：详情模式回填依赖登录态**

浏览器端（localhost，无登录态）详情模式显示「已答 0」。用 Node 带 jq 票据直连
`srvdaq_init_view_select`（mode=use）确认服务端**有**该批次的 `user_data` 4 条，
所以「已答 0」是票据/权限差异而非回填缺陷 —— 该服务对 `type=use` 要求调用方
具备相应身份，浏览器端无登录态拿不到。

**契约纠正**：select 请求体的 `page` 必须是对象 `{ pageNo, rownumber }`，
不是数字。写成 `page: 1` 会得到 HTTP 400
「Cannot deserialize instance of java.util.LinkedHashMap out of VALUE_NUMBER_INT」。
字段名是 `rownumber` 而非 `pageSize`。

**已知限制**：输入走原型 setter + 事件派发，不是真实键盘输入 —— 能验证组件的事件
绑定与状态更新，但不覆盖 IME、输入法组合等真实键盘行为。默认不提交，
`--submit` 才走最后一步，避免每次跑测试都产生真实记录。

**可访问性：输入框可读名称、按钮键盘可达与焦点可见性**（`pnpm a11y`，7 页 0 项问题）

问卷本质是表单，键盘操作与屏幕阅读器是刚需。用 Chrome **可访问性树**实测，发现
**四个真实缺陷**，修复前 7 个输入框与全部可点击元素中招。

**缺陷一：输入框对屏幕阅读器没有名称**

    <uni-input aria-label="所属单位">   → role=generic   name=「所属单位」
      └─ <input>                        → role=textbox   name=「」   ← 空

`aria-label` 写在 `<input>` 上会被 uni-app 留在外层 `uni-input`，而外层是
`role=generic`，**不是表单控件**。ARIA 属性不会继承，屏幕阅读器读到的仍是一个
没有名称的 textbox。用 `useAriaLabel` 组合式函数把名称写到真正承担控件角色的原生
元素上，修复后变为 `role=textbox name=「所属单位」`。

**这一段最初用的是自定义指令，后来推翻了**：小程序端的 vue 编译器**不支持自定义
指令**，模板里出现 `v-aria-label` 会让 `pnpm build mp-weixin` **直接失败**
（`[vite:vue] unknown directive`）。用 `#ifdef H5` 包住指令的钩子也不行 —— 条件编译
把 `mounted` / `updated` 删掉后导出的指令变成空对象，模板里的指令名仍然存在，
报错照旧。改成组合式函数后 `onMounted` 在两端都会执行，平台差异放到运行时判断。

**换成组合式函数后又踩一个坑**：`ref` 绑在 uni-app 的**内置组件**上时，Vue 赋给 ref
的是**组件实例**而不是 DOM 元素（没有 `matches` / `querySelector`）。直接当元素用会
**静默失败** —— `onMounted` 里的异常不冒泡到页面，页面上看不出任何异常，内层 input 的
`aria-label` 永远是 null。a11y 审计当时报「无名称 7 项」才发现。修复方式是统一解包
`$el`，并在写入失败时用 `nextTick` + `setTimeout` 重试（内置表单组件在 `onMounted`
时可能还没渲染出内部原生 `<input>`）。实测 `namedNativeInputs` 从 0 变 3。

**缺陷二：键盘用户看不到焦点在哪**

uni-app 内置样式把 outline 设成 none，实测聚焦前后完全一样（`outlineStyle: none`、
`boxShadow: none`、父元素边框色也不变），页面里**没有任何 `:focus` 规则**。
用 `:focus-visible` 补回来 —— 只在键盘聚焦时显示，鼠标点击不显示，不影响视觉简洁。

**选择器踩了两个坑，都靠实测才发现**

1. 首版 `:deep(.si-field__input:focus-visible)` 命中的是外层 `uni-input`，而真正被
   聚焦的是内层原生 input，**永远不会触发**。
2. 改成 `:deep(.si-field__input input:focus-visible)` 仍不生效：uni-app 的 postcss
   插件会把选择器里的 `input` **改写成 `uni-input`**，实际编译出
   `[data-v-x] .si-field__input uni-input:focus-visible`，还是外层元素。
   真实结构是 `UNI-INPUT > DIV.uni-input-wrapper > INPUT.uni-input-input`，
   必须落到 `.uni-input-input`（textarea 对应 `.uni-textarea-textarea`，
   两个类名都已在 uni-app 源码中核对）。

**测量方法本身的坑（差点把修好的当成没修）**

焦点检查最初用 `el.focus()` 程序化聚焦，7 个输入框全部报「焦点不可见」。但
`:focus-visible` 的设计就是**不响应程序化聚焦**（否则鼠标点击也会出现焦点环），
所以这个测量本身无效。改用 `Input.dispatchKeyEvent` 发**真实 Tab 键**后才测得准 ——
真实 Tab 下 outline 为 `solid/2px/rgb(0,122,255)`，正是主色 #007AFF。

**反向验证**：把焦点规则的选择器改坏 → 焦点不可见 10/10、退出码 1；
恢复 → 0 项、退出码 0。

**缺陷三：按钮对键盘完全不可用（最严重）**

    .bx-button:  tag=uni-view  role=(无)  tabindex=(无)  tabIndexProp=-1  cursor=auto
    可 Tab 到达:  只有 3 个 input
    真实 Tab:     Tab 4 直接跳到 body —— 按钮永远到不了

`BxButton` 用 `<view>` 渲染，H5 上是 `<uni-view>`，既没有 role 也没有 tabindex。
**键盘用户连「下一步，开始作答」都按不到，无法提交问卷**。`cursor: auto` 还让
鼠标用户看不出它可点。

修复：补 `role="button"`、`:tabindex="inactive ? -1 : 0"`（禁用/加载中移出 Tab
序列）、`aria-disabled` / `aria-busy`、Enter/Space 键盘激活（Space 要
preventDefault 否则页面滚动）、`cursor: pointer`、`:focus-visible` 焦点环。

**验证**（CDP 真实按键）：Enter 与 Space 聚焦按钮后 hash 都变为
`#/?activity_no=...&formType=form`，确实跳转到作答页。

**审计脚本自己的漏报（比误报更危险）**

`scripts/a11y.mjs` 的选择器只查 `button`，漏掉 uni-app 的自定义元素，于是报
「可交互 0 个」—— 而页面上明明有按钮。**漏报让审计看起来是绿的。** 改为覆盖
`uni-button / uni-input / uni-textarea / uni-picker / [role] / [tabindex]`，并新增
「键盘到不了」检查（`tabIndex < 0`）。补上后各页可交互元素从 0 变为 6 / 7 / 1 个。

**反向验证**：把按钮 tabindex 写死 -1 → 键盘到不了 6 项、退出码 1；
恢复 → 0 项、退出码 0。

**缺陷四：其余可点击元素同样键盘不可达**

按「修完一个实例就扫描同类」把 `src` 里所有 `@click` 扫了一遍，还有 4 处是
`<view>` / `<text>` 渲染的可点击元素：

| 位置 | 影响 |
| --- | --- |
| `BxNavBar` 返回键（‹） | 键盘用户无法返回上一页 |
| `RecordList` 记录卡片 | 键盘用户打不开记录详情 |
| `RecordList` 「点击加载更多」 | 键盘用户无法翻页 |
| `couple` 「查看结果 / 查看作答」 | 键盘用户打不开 |

统一补 `role="button"`、`tabindex="0"`、Enter/Space 激活、`cursor: pointer`、
`:focus-visible` 焦点环；记录卡片额外带 `aria-label`（题名 + 状态）。

**审计脚本自己的过严检查**

新增「键盘到不了」检查后报 4 项，但都是 `role=radiogroup` / `role=group` 的
**分组容器** —— 它们只是语义包装，本来就不该可聚焦。**一个含义错误的指标比没有
指标更糟**，所以排除分组角色（radiogroup / group / presentation / none /
list / listbox）。

**最终结果**：各页可交互元素 0 / 16 / 8 / 22 / 2 / 16 / 1，四项检查全部 0 项。

**页面冒烟：多端视口下的渲染与适配**（11 页 × 4 视口 = 44 次渲染 / 0 异常）

项目没有 @vue/test-utils，页面与组件层无法用单测覆盖 —— 这是测试保护面里最大的
一块空白。用 CDP 驱动 Chrome 无头遍历全部页面，检查渲染内容、未捕获异常、
console.error，并断言首屏文案（`pnpm smoke`，需先起 `pnpm dev h5`）。

**首次运行就发现了真问题**：`SuggestionPanel`（评估建议面板，评估结果页与调研结果页共用）
只校验了 `activityNo`，缺 `fillBatchNo` 时仍然发请求，服务端返回
「系统繁忙，请稍后再试」—— 那是网关兜底文案，用户看不懂、也无法据此判断该怎么办。

老工程 `assessmentResult.vue` 的 `onLoad` 是
`if (option.activity_no && option.fill_batch_no)`，**两个参数都有才发请求**，
新工程漏了这半个条件。现按同样语义拦截，但给出明确提示「缺少作答批次号」
（老工程是页面全空白，这点是有意改进）。

修复后同一页面：`系统繁忙，请稍后再试` → `暂无评估建议 / 该问卷可能未配置建议内容`。

**冒烟脚本自身的三处修正**（都是工具问题，不是产品缺陷，但会直接影响结论可信度）：

| 现象 | 真实原因 | 处理 |
| --- | --- | --- |
| 首轮 5 页报「空白」 | Vite dev 按需编译未完成，固定 sleep 把「编译慢」误判成「白屏」 | 轮询到有内容为止（最多 14 秒） |
| 空态页报「白屏」 | markers 要求 `.bx-container`，而空态/错误态本就不渲染它 | 只确认页面壳挂上，渲染判定看文本长度 |
| 「缺批次号」页测出有批次号 | uni-app 的 `onLoad` 只在页面首次创建时执行，同路径不同 query 复用组件实例、参数残留 | 每页导航前先回 `about:blank` |

最终 11 个路由（含一个专门验证缺批次号文案的用例）全部通过、0 异常。

**多端视口与横向溢出**

用户明确要求同时适配 PC 与移动端，小程序还要竖屏/横屏两套布局，公众号 H5 也要
兼容，所以冒烟按 4 个视口各跑一遍全部页面：

| 视口 | 尺寸 | 说明 |
| --- | --- | --- |
| PC | 1440×900 | |
| 移动竖屏 | 375×812 | |
| 移动横屏 | 812×375 | |
| 公众号H5(微信内置) | 375×812 | UA 换成含 `MicroMessenger` 的微信 UA |

每个视口下新增**横向溢出**检测（`scrollWidth - innerWidth`）—— 这是最典型的
适配缺陷，窄屏下卡片、表格、长文本很容易撑破视口，表现为整页可以左右拖。

#### 地址题第一版把整张表当成了第一列（重要）

老工程「地址」题用的是 `isTree: true` 的**树形级联**：

```js
// 老工程 questionnaire/index/index.vue 的 '地址' 分支
config.type = 'cascader'
config.srvInfo = {
  serviceName: 'srvconfig_area_adj_select',
  appNo: 'config',
  isTree: true,
  column: 'no',
  showCol: 'path_name',
}
```

**`isTree: true` 是关键**：一次取回**整张表**，由组件在客户端建树分层。
所以 `srvconfig_area_adj_select` **无条件返回整张表是有意的设计**，不是「数据没过滤」。

我第一版实现把「无条件查询的结果」直接当成第一列 —— 省/市/区**全混在一列**，
用户可以把一个区选成「省」。**这就是「取回整张表」被误当成「取回顶层」的后果。**

改成：一次取回 → `buildAreaTree` 建树 → 换列时从内存取下级。附带好处是
**级联不再逐级发请求**，也就不再有「先发的后返回、市列表被旧省份覆盖」的时序问题。

**根节点怎么判断（不猜标记）**：`parent_no` 为空，**或者**它不在「所有节点的编号」集合里，
就是根。这样 `parent_no = '0'` 和 `parent_no = null` 两种约定都能命中 ——
**生产用哪种标记我从数据里看不出来，所以干脆不假设。**

##### 连带修掉的两个真 bug

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 拖动后确定得到 `bxq测试省2 / bxq测试市A`（省2 配上省的市） | `applyColumns` 把 `indexes` **一律归零**，等于告诉 picker「第一列选的是索引 0」，而第二列已是另一个上级的下级 | 索引落在**路径**上：`findIndex(node => node.no === path[level])`，只有新出现的末列才默认 0 |
| 滑动后**取消**，控件仍显示从没确认过的选择 | `onColumnChange` 直接改 `labels`（而 `labels` 是「已确认」的展示文案） | `onColumnChange` 不再碰 `labels`；`onConfirm` 时从 `columns`/`indexes` 重新算 |

第一条是**改了字段名却漏改模板**的连带产物：我把节点字段从 `name` 改成 `label`，
忘了 `range-key="name"` —— 类型检查、单测、lint **全部绿**，界面却是空列。
**这就是「改动静默失效」**：静态检查抓不到模板里的字符串。

##### 变异验证

| 变异 | 结果 |
| --- | --- |
| `buildAreaTree` 把所有节点都当根（退回原缺陷） | 第一列变成全部 8 个节点 `["bxq测试省2","bxq测试市C","bxq测试区C1","bxq测试省",…]`，3 项失败 |
| `applyColumns` 把索引一律归零 | 控件显示 `bxq测试省2 / bxq测试市A`，1 项失败，断言消息直接点名错配 |

##### 断言自身也修了两次

- 「第一列只有顶层节点」原本写的是 `topLevel[0].length === 1` —— 顶层本来就可能多于一个
  （本环境加了第二个省之后就是 2 个），**用项数当判据会随数据变化而假红**。
  改成「第一列里没有混进下级节点」（判据是标签里不含「市/区」）。
- 「换上级后第二列是新的下级」原本从**列的项目列表**里读当前选中项 ——
  列表是全部候选项，**索引变了列表不变**，于是这条永远看不出变化。
  改从 `.uni-picker-select .uni-picker-item.selected` 读各列真正选中的文案。

##### 只有 1 个顶层节点时无法验证联动

顶层只有 1 个节点时 column 0 根本改不了，**级联在结构上不可能触发**。
拿这种数据去验证联动是「测量前提错了」，所以脚本在顶层 < 2 时
**显式打印跳过原因**（跳过的检查必须是响亮的），而不是默默通过。
为此补了第二个顶层省（`bxq98` → `bxq9801` → `bxq980101`），现在共 8 行测试地区。

**保留的空态守卫：无数据时不弹出空转轮。** uni 的 `<picker>` 在 `range`
为空时**照样会打开**，用户只看到「取消 / 完成」和一个空的选择器，会以为页面坏了。
现在顶层没有可选项时直接禁用，并如实显示「暂无地区数据」——
本环境修好 app 之后这条分支不再触发，但换个没有地区数据的部署仍会遇到，
所以 `special-e2e` 按**实际数据分支**断言（有数据验证级联、无数据验证诚实降级），
而不是写死某一种。

这条断言**一开始写错了、而且是假绿**：先写的是查 `getAttribute('disabled')` 是否
`!== 'false'`，去掉守卫做变异后属性值变成空串 `""`，断言照样通过。改成**行为断言**
（点它、看有没有弹层）后，变异立刻产生失败，并打印出弹层内容正是「取消 / 完成」——
即修复前用户会看到的东西。**属性值能骗过断言，行为不能。**

**同类扫描**：`BxImageField` 的附件查询失败曾被 `catch { rows = [] }` 吞掉（见限制 2），
`BxRefSelector` 的空态掩盖错误（见上），地址题的空转轮，三者是同一类问题的三个实例 ——
**「加载失败」与「确实没有数据」永远不能共用同一个界面**。

**结果页的服务端作答语义**（CDP 真实浏览器 + 真实网关）

伪造三个服务的响应验证结果页完整渲染时，确认了 `svalue` 的真实形态并修掉三处问题：

`srvdaq_record_reply_merge_select` 的 `svalue` 对选项题返回的是**选项序号**
（`option_view_no`，实测单选返回 `"1"`、`"2"`），不是选项文案：

| 题型 | 真实 `svalue` |
| --- | --- |
| 单选 | `"1"` / `"2"` |
| 多选 | `"2"` / `"3"`（**只返回一个值**） |
| 文本 | 作答原文 |
| 数字 | `"2026.00000"`（带小数尾巴） |

三处修复：

1. **「我的作答」显示序号**：直接渲染会让用户看到「我的作答：1」。
   还原为选项文案的逻辑落在 `serverAnswersToAnswerMap`（服务端值 → 作答映射）
   与 `describeSelected`（作答映射 → 展示文案）两处，兼容序号 / `option_no` / 文案三种形态，
   匹配不上时保留原值便于排查；数字题去掉小数尾巴。
   （早期这里还有一个独立的 `describeServerValue`，因为它已无生产调用方、只被测试引用，
   已删除，行为并入上述两处。）
2. **统计与逐题作答数据源不一致**：统计用本地回填（`init_view_select` 的 `user_data`），
   逐题用服务端 merge。当 `type=use` 失败但 merge 成功时（如已登录但非活动创建人），
   会出现「逐题显示有作答、统计却全是 0」。新增 `serverAnswersToAnswerMap` 统一以服务端为准。
3. **纯空白作答值被当成有作答**：原来的空串长度检查挡不住 `"   "`，会让没答的题算成答错。

浏览器回归：选项题显示「选项甲」而非「1」，多选显示「多选甲、多选乙」，
统计由 `0 答对/0 答错/2 未答` 变为 `2 答对/0 答错/0 未答`，无 JS 异常。

**统计口径**：`calcScore` 会跳过**没有配置正确答案**的题（文本题等），
它们不计入总分、也不计入「未答」。因此「2 答对 / 0 未答」里的分母只是客观题，
不是全部题目 —— 这是评分语义，不是统计遗漏。

| 11 | `record_reply_select` 默认带 `order` | 该服务传 order 静默返回 0 条，记录列表恒空、结果页拿不到服务端得分 | 默认不传，显式要求时才带 |

**根因与对策**：第 1–9 处源于"凭接口名推测契约"，第 10 处源于"只读了数据产生点、没看下游消费点"，第 11 处源于"把平台的宽容当成支持"。对策固定为：**先读老工程源码，再用实测验证**；实测能证明"会不会炸"，但**语义正确性只能靠源码**（第 8 处即"实测通过但依据不足、仍予删除"）。

**关于第 11 处的额外教训**：它被两件事掩盖 —— 浏览器端曾误判为「拿不到会话」（实为探测脚本漏带票据头，记录页因此显示错误态而非空列表）、结果页有本地计算兜底。**只有真机才会暴露**。而契约测试当时锁的是"默认排序"这个错误行为，说明**契约测试本身也需要实测校准**，不能只锁"当前实现长什么样"。

## 五、平台行为实测：静默失效清单

这类问题的共同点是**请求不报错、页面正常渲染**，只有真实数据才能发现。集中记录，避免重犯。

| 服务 | 参数 | 实际行为 | 本工程做法 |
| --- | --- | --- | --- |
| `srvdaq_record_reply_select` | `order` | 传任何排序字段（`start_time`/`end_time`/`id`/`create_time`，asc 或 desc）都**返回 0 条且不报错** | 默认不传，显式要求时才带 |
| `srvdaq_record_reply_merge_select` | `order` | 传 `order` 直接 **FAILURE** | 不传 |
| `srvdaq_record_reply_merge_select` | `condition: activity_no` | 报 `CONDITION_COLUMS_NOT_EXISTS`（服务列里没有 `activity_no`） | 只传 `fill_batch_no` |
| `srvdaq_init_view_select` | `order` | **非必需**：带 `item_seq asc` 与不带都返回同样条数 | 带上（无害，且与老工程一致） |
| `srvdaq_activity_sug_select` | `condition: activity_no` | 必需；测试活动无建议数据时返回 0 条且 SUCCESS | 传 `activity_no` + 可选 `fill_batch_no` |
| `srvdaq_record_reply_select` | `condition: []` | 直接 **FAILURE** | 始终至少给一个条件 |
| `srvfile_attachment_select` | `condition: []` | 正常返回（实测 3 条） | 按 `file_no eq` 查询 |
| `srvconfig_area_adj_select` | `condition: []` | SUCCESS 但 0 条（**测试环境该表无数据**） | 顶层不传 `parent_no` |
| 写操作 | — | `result_submit` 返回的 `fill_batch_no` 在 `response[0].response`；草稿保存第二次起 `response` 为 `null` | 按此解析 |

另外注意**写入后立即查询存在可见性延迟**：提交成功后马上按 `activity_no` 查会返回 0 条，数秒后再查才出现。结果页因此不能假定"提交完就能立刻读到服务端得分"，本地兜底是必要的。

**关键结论：同一个参数在不同服务上的表现并不一致。**

| 参数 | 服务 A 的行为 | 服务 B 的行为 |
| --- | --- | --- |
| `order` | `record_reply_select`：静默返回 0 条 | `record_reply_merge_select`：直接 FAILURE |
| `condition: []` | `record_reply_select`：直接 FAILURE | `srvfile_attachment_select`：正常返回 |
| `order` | `init_view_select`：非必需（带不带一样） | `record_reply_select`：带就废 |

所以**不能从一个服务的行为推断另一个，必须逐个实测**。这条已经三次被验证。

**同类教训（已第二次遇到）**：契约测试如果只断言「当前实现长什么样」，会把错误行为一起锁进测试，让它看起来「有覆盖、很安全」。

- 第 42 轮：测试锁住了 `record_reply_select` 的错误默认排序，改对之后测试反而失败；
- 第 46 轮：测试锁住了 `record_share_add` 的 `share_type: '朋友圈'` 默认值 —— 分享给好友会被静默记成朋友圈，渠道数据失真。

两处都已改为断言正确行为。**写契约测试时先问一句：这个默认值是「后端契约要求」，还是「我顺手写的」？**

### 页面参数与 URL 约定

所有页面统一用 `src/utils/query.ts` 的 `readQuery()` 读取参数 —— 它做安全解码，
遇到含裸 `%` 的值（如活动标题「完成率 100%」）会回退原值，而不是抛 `URIError` 打白屏。
此前 9 个页面各写一套，两个 history 页对 `title` 裸调 `decodeURIComponent` 且无任何保护。

| 参数 | 消费方 | 说明 |
| --- | --- | --- |
| `activity_no` | 全部业务页 | 系统生成，纯数字，解码幂等 |
| `fill_batch_no` | 答题 / 结果 / 记录页 | 32 位十六进制 UUID，解码幂等 |
| `formType` | 答题页 | `form` / `detail` / `view`，纯英文 |
| `title` | 两个 history 页 | **外部入口传入，可能含中文，必须解码** |
| `status` | **无** | 老工程遗留的**死参数**：全工程无任何读取点 |

`status` 目前仍被 4 处跳转拼接（`RecordList`、`cover`、`submitInfo`、`couple`），
其中 `index/index.vue` 的分享路径 `status=进行中` 与老工程一致、已对外发布，故保留不改。
**它的值含中文且未编码**，将来若有页面要读它需一并处理编码，否则小程序端可能解析异常
—— 这也是「保留但记录」而非「直接删除」的原因。

### 1. 逐题判对错（更正此前结论）与多选丢值

真正需要平台侧处理的限制是**多选丢值**：

| 来源 | 批次 `d9102bc9…` 第 2 题（正确答案 `1、2`） | 据此判分 |
| --- | --- | --- |

业务请求层会自动带票据，因此正常使用不受影响。

### 2. 图片上传（**已实现，此前的「无权限」结论是错的**）
> **更正**：此前记「`srvfile_attachment_add` / `srvfile_attachment_upload` / `srvfile_upload`
> 均返回无权限，需平台侧开通」。**这个结论建立在错误前提上** ——
> 我把上传的端点定在了**标准** `{app}/{action}/{service}` 形状上，而那三个服务名
> 本身就是猜的。真实端点是**专用路径**：

```
POST {gateway}/file/upload     multipart FormData
  serviceName   = srv_bxfile_service
  interfaceName = add
  app_no        = <应用>
  file_no       = <批次号，可选>
  file          = <文件>
票据只放 header
```

实测（2026-10-11，parkDev）：

| 事实 | 实测依据 |
| --- | --- |
| 端点可用，**不需要额外开通权限** | HTTP 200，响应含 `fileurl` / `file_no` / `create_user: jq` |
| 走标准路径会报「非法API」 | `/file/operate/srvfile_attachment_add` → `非法API[operate/srvfile_attachment_add]请求` |
| 响应是**裸对象**，无 `state`/`resultCode` 信封 | 返回体只有业务字段 |
| 成功判据是 `fileurl` 非空 | 契约同此 |
| `file_no` 是**批次号**：传已存在的值 → 追加 | 传已存在值后，该批次下变成 2 个文件 |
| 传**不存在**的 `file_no` → 被静默忽略，服务端另生成 | 传 `batchno_custom123`，响应 `file_no` 是服务端生成的 |
| 浏览器端 `uni.uploadFile` 同样可用，票据 header 被采信 | CDP 在页面里实跑，响应 `create_user: jq` |
| `/file/delete` 体 `{fileurl}` 可用 | 返回 `resultCode: SUCCESS` |

**实现**：`@/api/file/upload` 的 `uploadAttachment`（`uni.uploadFile`，三端统一）+
`BxImageField` 的上传/逐张移除/清空 UI。**每张图各自成批**（上传不传 `file_no`），
作答值是**批次号列表**，一个元素一张图。

#### 图片题改成「文件列表」：逐张移除曾经不可表达

**旧状态**：作答值是**一个批次号**，同题多图共用它。删中间一张只能新建批次把剩下的重传
（本地没有文件字节，做不到），或改作答值形状。所以逐张移除**不可表达** ——
硬做的效果是「界面少一张、刷新又回来、提交的作答值也没变」，即假操作。
当时只提供「清空图片」。

**现在**：一张图一个批次号，逐张移除 = 去掉一个元素（引用移除，不动服务端文件）。
复用的是平台自己的多值机制 —— `option_data` 本来就是数组，多选就是这么存的，
没有发明新协议。

兼容性：旧数据是**一个**批次号，正好等于「长度为 1 的列表」，读法完全一致，
**不需要迁移**（有单测把这条钉住：`legacy` 与 `['<同一个值>']` 必须解析成同一个结果）。

##### 为什么作答值里**不能存文件路径**（实测，差点又犯「凭直觉设计」的错）

最直觉的做法是把路径存进作答值，但**存不进去**。第一次改完，界面和请求体全都对，
e2e 的 7 条新检查也全绿 —— 只有「提交后跳到结果页」红了。追下去才发现：

| 提交给**图片题**的值 | 结果 |
| --- | --- |
| 路径 `/20261011/.../x.jpg`（55 字符） | `FAILURE Data truncation: Data too long for column 'option_value'` |
| 字母 ×50 | SUCCESS |
| 字母 ×52 | 同上失败 |
| 字母 ×64 | 同上失败 |
| 同样的 64 字符给**文本题** | SUCCESS |

结论两条：

1. **图片题的 `option_value` 上限约 50 字符**，比文本题短得多。批次号是 20 位数字，
   放得下；路径放不下。「作答值存路径」在当前后端下是**走不通的**，不是设计取舍。
2. 图片题的作答值**可以是多值**：提交两个批次号 → `SUCCESS`，
   回读 `srvdaq_record_reply_merge_select` 得到**两行**图片 `svalue`，与多选一致。

> **教训**：这次 e2e 有一条检查只断言了**请求体**，于是「提交静默失败」被当成通过。
> 现在提交后额外抓 `Network.getResponseBody`，断言响应里是 `SUCCESS` 且不含 `FAILURE`。
> **断言请求 ≠ 断言成功** —— 这是「断言一个被 mock 掉的边界的入参，不等于断言真实行为」
> 的同类错误，只是这次边界换成了真实服务端。

##### 变异验证

| 变异 | 结果 |
| --- | --- |
| `onRemove` 里把 `fileNos.filter(item => item !== fileNo)` 改成 `fileNos`（空操作） | 3 项失败：`移除后只剩一张`、`移除后计数变成 1 / N`、`移除一张后提交值只剩一个批次号 —— 实际 2 个` |
| `imageAnswerTargets` 去掉 `split(',')` | 单测「逗号分隔的多个批次号」失败 |

变异复现的正是「假操作」症状：界面少一张、提交值仍是 2 个。

##### 刻意不做「真删文件」

逐张移除只做**引用移除**（改作答值），不调 `/file/delete`：
真删会让服务端文件消失，而同一张图可能还被草稿或历史作答引用。
这是平台惯例里明确写的顺序（「先引用移除，确认删除才调 `/file/delete`」）。

#### 回显曾读不到附件 —— 真因是**请求打错了应用**（重要，第二次更正）

我一度记「上传端点可用、但 `srvfile_attachment_select` 无权限，需平台侧开通」。
**这个结论也是错的**，而且是同一个错误的第二次：**请求打到了默认的 `daq` 应用，
而这个服务在 `file` 应用下。**

| 请求 | 结果 |
| --- | --- |
| `POST /bxapi/daq/select/srvfile_attachment_select` | `state=FAILURE`，`msg=srvfile_attachment_select无权限访问` |
| `POST /bxapi/file/select/srvfile_attachment_select` | **`state=SUCCESS`，正常返回附件行** |

根因在 `bxSelect`：

```ts
// 修复前：app 只从第二个参数读
export async function bxSelect(params, options = {}) {
  const result = await request({ ...options, action: 'select', service: params.serviceName, data: params })
  return result
}
```

而 `area.ts` / `attachment.ts` 都把 `app` 写在**第一个参数** `params` 里。于是：

1. `params.app` 被静默忽略，URL 用了默认的 `daq`；
2. `params` 整体又是请求体，**body 里 `app: 'file'` 看着完全正确**，把 bug 藏住了；
3. 服务返回「无权限访问」—— 看起来像平台权限问题，实际是自己调错了应用。

**受影响的不是一处，是两个题型**：`srvfile_attachment_select`（图片回显）
和 `srvconfig_area_adj_select`（地址题）。地址题的表现是**永远**显示「暂无地区数据」，
而它其实是**有数据的**（该服务无条件返回 5 行）。

修复：`bxSelect` 现在读 `params.app`（第二个参数 `options.app` 优先级更高），
并在 `BxSelectParams.app` 上写明「决定 URL 的 `{app}` 段」。新增 3 项单测直接断言 **URL**：

| 用例 | 断言 |
| --- | --- |
| `params.app='config'` | URL 含 `/config/select/...`，且**不含** `/daq/` |
| 不传 `app` | 回落 `/daq/` |
| 第二个参数传 `app` | 优先级更高 |

变异（去掉 `params.app` 传递）→ 第 1 项立刻失败。修复后浏览器实测：地址弹层显示
「bxq测试省 / bxq测试市A / bxq测试市B / bxq测试区A1 / bxq测试区A2」，
图片回显切回 `/file/download` 服务端地址。

**为什么原有测试没抓住**：`test/api/area.spec.ts` 把 `bxSelect` **打了桩**，
只断言 `params.app === 'config'` —— 参数传对了，URL 却是错的。
**断言一个被 mock 掉的边界的入参，不等于断言真实行为。**

本地预览兜底（`resolveImageDisplay`）**保留**：它不是为这个 bug 写的补丁，
而是「附件查询真的失败」时的安全网（网络抖动、真实权限变更）。
判定规则仍是纯函数，7 项单测锁住；两条变异（`localOnly` 恒 false、
不用服务端列表）分别产生 3 / 2 项失败。

#### 回顾页曾把「照片」和「问卷」显示成内部编号

修好 app 之后才暴露出第二个问题：**图片题、引用题、地址题的作答值都是内部编号**，
而回顾页直接把它们当文本渲染。

| 题型 | 作答值的真实含义 | 修复前显示 | 修复后显示 |
| --- | --- | --- | --- |
| 图片 | 文件**批次号列表**，如 `['20261011121039186100']` | 那串数字 | 缩略图（`/file/download?filePath=...`） |
| 引用 | 被引用记录的 `refed_col` 值 `20261011113133000003` | 那串数字 | 被引用记录的标题（`bxq 特殊题型测试问卷`） |
| 地址 | 地区编号 `bxq99` | 那串编号 | 地区名称（`bxq测试省`） |
| 读不到时 | — | 同上（误导） | 「已上传图片（图片暂时读不到）」/ 回退原值 |

**用户上传的是照片、选的是问卷和地区，看到的却是编号** —— 三个题型是同一类问题。

实现：

- `imageAnswerTargets`（`@/domain/questionnaire/images`）挑出「图片题且值非空」的题，
  逐个批次号查 `srvfile_attachment_select` 换出真实地址（多值逐个返回，与多选同构）。
- `parseRefConfig` / `refAnswerTargets` / `pickRefLabel`（`@/domain/questionnaire/refs`）
  解析引用题的数据源配置并换出展示列。**这段解析原先只写在 `BxRefSelector` 里，
  现在抽出来两处共用一份** —— 没有抄第二遍（抄第二遍正是本项目反复出现的缺陷模式）。
- `addressAnswerTargets` / `pickAreaLabel`（`@/domain/questionnaire/addresses`）
  按编号查地区换出名称，展示列优先 `path_name`、**必须回退 `name` 而不是 `no`**
  （实测本环境 `path_name` 为 null，直接回退编号就是要避免的东西）。

单测：图片 5 项、引用 8 项、地址 7 项（共 396 项）。变异验证：

| 变异 | 结果 |
| --- | --- |
| 让 `loadAnswerImages` 不执行 | 2 项失败 |
| 把图片题的 `mine` 改回原值且关掉图片分支 | 行文本变成 `20261011130002195100`，4 项失败 |
| 把引用题的 `mine` 改回原值 | 行文本变成 `20261011113133000003`，2 项失败 |
| 把地址题的 `mine` 改回原值 | 行文本变成 `bxq99`，2 项失败 |

后三条变异打印出的正是**修复前用户会看到的东西** —— 断言确实复现了原缺陷，
而不是只覆盖了新写的代码。

> **这是「修完一个实例就扫描同类」的价值**：app 那个 bug 修好后才露出
> 回顾页展示内部编号这一族问题；图片题修完后再扫一遍，又找到引用题和地址题
> 两个同族实例。**只修被报告的那一个，另外两个会留下来。**
>
> **扫描的收尾证据**：按题型逐个核对「作答值是不是内部编号」，并查了本环境
> 全部 45 道题的题型分布 —— `单选 21 / 数字 13 / 文本 6 / 多选 2 / 地址 1 /
> 图片 1 / 引用 1`，**7 种全部被 `mapper` 处理，没有落到 `unknown` 的**。
> 其余题型的作答值本身就是展示文案（文本/数字/日期/时间），选项题已还原成选项文案。
> 所以这一族问题到此为止，不是「大概还有」。

> 断言也写错过一次：「图片题行标注『已上传图片』」在缩略图渲染出来时必然失败，
> 因为那时不该再显示文案，改为「缩略图或文案有其一即可」。
> 引用题那条一开始写死了某个活动名，改成与**实际选中的那一项**比对。

#### 端到端验证（`pnpm special-e2e`）

为了让这条链路有真实数据可跑，新建了活动 **`20261011113133000003`**
（「bxq 特殊题型测试问卷」，4 题：图片 / 引用 / 地址 / 文本），
**没有动**现有测试活动 —— 后者被 e2e/smoke 断言了「共 4 题」，加题会连带改掉那些断言的前提。

验证方式与覆盖边界：

- **选图弹窗用桩替换**。headless Chrome 里 `input.click()` 会**立即触发 `cancel` 事件**
  （没有真实文件选择器可开），uni-app H5 的 `chooseImage` 监听 cancel 并
  `reject('chooseImage:fail cancel')`，组件于是按「用户取消」静默返回 ——
  之后注入的 `change` 事件已经晚了。实测证据：
  `CHOOSE_CALL#1 → CHOOSE_FAIL#1 {"errMsg":"chooseImage:fail cancel"}`（点击瞬间），
  随后 `DOM.setFileInputFiles` 才触发 `change`。这是**环境限制，不是产品缺陷**。
- 桩只替换**平台选图弹窗**这一步，返回真实 PNG 的 blob URL（**一次给两张**，
  否则列表长度为 1，「逐张移除」与「清空」分不出来）；
  下游（multipart 组装、票据 header、服务端落库、回显、逐张移除、作答值写入、
  提交请求体、**提交响应**）**全部是真实链路**。
- 56 项检查全绿。关键断言：`/file/upload` 返回 HTTP 200；
  **提交响应是 `SUCCESS` 且不含 `FAILURE`**；
  提交体含图片题且 `option_data` 是**批次号列表**（移除一张后实测 `["20261011152719741100"]`）；
  结果页把该批次号还原成缩略图、且不展示编号。
- 回显地址是服务端地址**或**本地预览，且走本地预览时必须有解释提示。

**未被覆盖的**：选图弹窗本身的交互（原生行为，headless 无法验证）；微信小程序端真机。

**实测到的差异（不影响显示，仅记录）**：uni-app H5 的 `uploadFile` **不沿用原文件名**，
`src_name` 变成 `file-<时间戳>`，且把 png 存成了 `file_type=jpg`。
图片显示走 `/file/download?filePath=`，实测能正常取回，故不处理。

**教训**：报「无权限」之前，先确认自己**调对了端点**。服务名是猜的、端点形状也是猜的，
两个猜测叠在一起，得到的错误结论看起来却很像平台配置问题。

**教训二**：`catch { 当作空 }` 是**静默失败**的温床。查询失败和「确实没有数据」
是两种状态，界面上必须能区分 —— 否则用户看到的是「没传上」，实际是「传上了但读不出来」。

### 3. 服务的鉴权与权限要求（实测校正，含两次修正）

> **本节经过两次修正，保留结论与教训。**
>
> **修正一**：早期把浏览器端与 Node 端的差异归因于「平台会话 cookie 的用户身份覆盖票据身份」，
> 并据此推断「跨域拿不到数据、同域正常」。该归因是错的 —— 差异其实来自**探测脚本漏带票据头**。
>
> **修正二**：随后又得出「鉴权只按票据、与会话 cookie 完全无关」的结论，**这个结论也过于绝对**。
> 补充实测发现：**按用户维度查询**（`condition` 里带 `user_no`）时，平台还要求**调用者的会话身份**，
> 无会话时**静默返回空结果**（`state=SUCCESS` 但 `data` 为空），**不报错**。

用同一浏览器、同一票据逐项实测（应用内 `uni.request` 与页面 `fetch` 对照）：

| 服务 / 参数 | 结果 | 真实原因 |
| --- | --- | --- |
| `srvdaq_record_reply_select`（只按 `activity_no`） | **成功**，返回 20 条 | 按票据即可 |
| `srvdaq_record_reply_select`（**加 `user_no` 过滤**） | **`SUCCESS` 但 0 条** | 平台要求**调用者会话身份**，无会话时静默返回空 |
| `srvdaq_init_view_select`（无 `type`） | **成功** | 无需登录 |
| `srvdaq_init_view_select` + `type=use` | FAILURE「非活动创建人，无法查看其它用户填写信息」 | **业务校验**：调用者须为活动创建人 |
| `srvdaq_record_reply_merge_select` | **成功**（带票据）/ `0011` 需要登录访问（无票据） | 需要登录态，请求层已自动带票据 |
| `srvdaq_item_cfg_select` | ~~FAILURE `0011`「无权限访问」~~ **2026-10-11 复核：SUCCESS 41 行** | 权限已开通，结论作废 |

**同一条件在 Node 与浏览器结果相反**（决定性对照）：

| 条件 | Node 直连 | 浏览器（无平台会话） |
| --- | --- | --- |
| `user_no = jq` | **11 条** | **0 条** |

说明过滤在**网关层按会话身份**处理，而不是在数据层按条件过滤。真实用户在自己的浏览器里
已登录平台（有会话），因此能查到自己的记录 —— **这不是代码缺陷**。

**为什么本机复现不了**：测试用 `localhost:5174` 访问，该域下**没有** `192.168.0.214`
的会话 cookie，因此无法模拟真实用户的登录态。这也是 `couple`（我的测评）与
`history` 在带 `user_no` 时显示空列表的原因。

**两次修正的共同教训**：都是**探测手段本身有缺陷**（漏带票据头 / 缺会话身份），
却顺势得出了关于服务行为的结论。这已是同一类问题的第 7、8 次 ——
**报结论前必须确认探测手段是对的，并做交叉对照**（不同调用方式、Node 与浏览器）。
唯一可靠的办法是**同条件多路径对照**。

页面据此区分两种状态：服务端明确返回「无作答」时显示「未作答」，
请求失败时显示「暂无法获取」，**不把「数据不可用」谎报成「未作答」**。


**关键推论（影响业务，非仅本地）**：该活动的 `perm_type` 是「匿名访问」，而 merge 需要登录态。
也就是说**匿名作答的用户在任何环境下都拿不到逐题作答值**，不只是本地开发受限 ——
这是平台侧的权限设计，前端无法绕开。刚提交完的当次结果页仍可用本地回填值正常显示作答。
此点已列入「待业务确认」。

### 4. favicon 在子路径部署时取不到（仅影响图标）

uni-app 生成的 `<link rel="icon" href="static/logo.svg">` 不带子路径前缀，设置 `h5.favicon` 无法改变该行为。仅影响标签页图标，不影响功能；如需修复可在部署侧补 `/static/logo.svg` 反向代理。

### 5. 草稿保存会在服务端逐条新建记录（老工程同样如此）

实测（浏览器抓包 + 记录查询）：`srvdaq_activity_result_save` **每次调用都会新建一条记录**，
即便请求里带了 `fill_batch_no`，响应仍回传一个**新的**批次号，传入值不被当作复用键。
因此逐题即时保存会在服务端留下多条「未完成」草稿。**老工程行为完全相同**
（`indexyax.vue` 也逐题保存、也传批次号），不是本工程引入的问题；
在「后端接口不变」的约束下前端无法消除，故不处理，仅记录。

前端能做且已做的是**不让批次号漂移**：只在首次保存锁定批次号，之后忽略响应回传的新值
（对齐老工程 `if (data.fill_batch_no && !self.fill_batch_no)`）。
否则同一次作答会被割裂到多条草稿，提交只能挂到最后一条上，其余成为孤儿记录。

**本地草稿续答**：服务端草稿是「逐题一条记录」且需要网络，因此答题页额外在本地
（`bxq:draft_answers:<activity_no>`，按活动隔离）同步一份答案快照，刷新或闪退后可直接恢复。
这条路径不依赖权限，匿名用户同样可用 —— 而服务端 `user_data` 回填受权限约束（见限制 3）。

续答与作废的完整语义（均已端到端实测）：

| 场景 | 行为 |
| --- | --- |
| 作答后刷新页面 | 答案与批次号都恢复，继续在同一批次上作答 |
| 提交成功后 | 批次号与本地草稿一并清空，下次进入是新作答 |
| 提交前离开再进入 | 保留草稿，属于续答 |

注：老工程用 `beforeDestroy` 在离开答题页时清空批次号，但**实测 uni-app H5 端该钩子不触发**
（页面由 uni 路由栈管理），小程序端却会触发 —— 依赖它会造成两端行为不一致，故未采用。
改由「提交成功后清除」覆盖真正需要防脏的场景；这也顺带修掉了老工程的一个缺陷：
它 H5 端提交后 `fill_batch_no` 残留，再次进入会把新作答写进已完成的那条记录。

**测试数据的自然结果**：联调期间该活动下已累积多条草稿记录，
清理时机见「待业务确认」。

### 6. 作答记录的归属过滤是体验层门槛，不是安全边界

`srvdaq_record_reply_select` **不按调用者身份过滤**：不带 `user_no` 条件时，
按 `activity_no` 查询会返回该活动的**全部**记录（实测匿名也有 100 条）。
而记录卡片点进去会带 `fill_batch_no`，`init_view_select` 的 `type=use`
会**如实返回该批次的 `user_data`** —— 也就是能看到别人的作答内容。

前端已加归属过滤（见「服务的鉴权与权限要求」一节的实测与判定依据），
但**这是体验层门槛**：直接手改 URL 带上别人的 `fill_batch_no`，服务端仍会返回数据。
真正挡住越权读取必须由平台按调用者身份过滤 —— **待平台侧配置**。

未登录时的判定依据是本机记录过的批次号（`bxq:my_batches`），因此：
换设备、清浏览器数据、或换浏览器后，**自己以前的记录就看不到了**。
这是「拿不到身份」时唯一可用的依据，页面会如实提示「未登录，仅显示本机作答记录」。

### 7. 票据过期有**两种**表现，第二种是静默的（排障必读）

票据过期不只有「报错」一种样子：

| 表现 | 现象 | 影响范围 |
| --- | --- | --- |
| **显式** | `resultCode=0011` + 「请求服务[x]需要登录访问」 | 前端能识别，会触发 `TICKET_EXPIRED` |
| **静默** | `state=SUCCESS` 但 `data: []`，**不报错、不提示** | 只影响**需要会话身份**的查询（`condition` 带 `user_no`） |

静默那种最坑：`srvdaq_init_view_select` 照常返回数据，页面看着一切正常，
但 `couple`（我的测评）这类按 `user_no` 过滤的查询恒返回 0 行，
界面显示「暂无已完成的测评」—— **看起来像业务没数据，实际是票据降级**。

**实测证据（2026-10-11）**：

```
旧票据：record_reply_select + user_no=jq + state=完成 → SUCCESS，data=[]（0 行）
新票据：同一请求                                     → SUCCESS，26 行
同一时刻 srvdaq_init_view_select 用旧票据仍 SUCCESS 返回 1 行
```

**排障规则**：当**一批互不相关的检查同时失败**（尤其是「查不到记录」类），
先刷新票据再怀疑代码。反之，若只有个别检查失败，才更可能是代码问题。

**代价记录**：本轮就踩了 —— e2e 出现 5 项失败、另一次 `--submit` 跑挂起 21 分钟，
排查方向一度指向 dev server 的 HMR 累积状态，重启无效；刷新票据后立刻全绿。
`init_view_select` 正常这一点**恰恰把注意力从票据上引开了**。

### 8. 输入框的可读名称：作者写了，但辅助技术读不到（uni-app 平台限制）

`<input aria-label="搜索问卷标题">` 在 H5 上**不会**把 `aria-label` 转发给真正被聚焦的
原生控件，而是留在了外层自定义元素 `uni-input` 上。

**实测（2026-10-11，Chrome CDP 读真实 DOM）**：

```
页面：/pages/editor/list/index
  INPUT.uni-input-input   aria-label=null   placeholder=null
  FORM.uni-input-form     aria-label=null
  DIV.uni-input-wrapper   aria-label=null
  UNI-INPUT（外层壳）      aria-label="搜索问卷标题"

页面：/pages/editor/design/index?activity_no=…
  三个控件（2 个 input + 1 个 textarea）全部同形：
  原生控件 aria-label=null / placeholder=null，壳上有 aria-label
```

`aria-label` 只对**自身**是无障碍树里的控件时才参与名称计算；`uni-input` 是通用
自定义元素，挂在它上面的 `aria-label` 不会被算作内层 `<input>` 的名称。所以：
**键盘能聚焦，屏幕阅读器读不出名字。**

**为什么不在页面里逐处修**：这不是某一页漏写，而是 uni-app H5 的统一行为，
14 个页面所有输入框都一样；逐页补也补不上（模板里没有可用的挂载点），
而自定义指令 `v-aria-label` 会被小程序编译器拒绝。要真正修掉需要在 H5 端做一次
运行时转发（把壳上的 `aria-label` 拷到内层原生控件），属于跨端基建改动，尚未实施。

**当前的处理方式**：`pnpm a11y` 按**逻辑控件**去重（外层壳 + 内层原生控件只算一个），
并把「名称只挂在壳上」的控件**单独计数报出来**，不计为失败但也不假装全绿：

```
问卷列表页（可交互 40 个）
  可读名称：全部有 ✓
  名称只挂在壳上 1 个（uni-app 未转发给原生控件，见 docs/验收清单.md「已知限制」）
…
== 平台限制：名称只挂在 uni-input / uni-textarea 壳上 1 项（不计为失败，但不等于屏幕阅读器能读到）==
```

> 审计只跑 375×812 视口。设计器在该宽度下只显示一个面板（另一个面板 `display:none`），
> 所以它的输入框不计入 —— 上表里设计器那一栏没有该提示，是**没测到**，不是「没问题」。

### 10.1 本环境**没有** `分节符` 题型（逐值探测结论）

首版演示问卷按老工程的分节符（`基本信息` / `满意度评价` / `补充信息`）来建，**第 1 道就被拒**：

```text
[问题条目类型]字段值数据类型不匹配
```

`bxdaq_item_cfg` 的 `item_type` 是 `Enum` 列，但 `option_list` 为 null —— 真实取值在元数据的
**`option_list_v2`** 字段里，端点：

```text
POST /bxapi/daq/select/srvsys_service_columnex_v2_select?colsel_v2=srvdaq_item_cfg_add
body: { condition: [ {service_name, eq, srvdaq_item_cfg_add}, {use_type, eq, add} ] }
```

实测枚举**只有 9 个值**：

```text
单选 / 多选 / 文本 / 数字 / 时间日期 / 图片 / 选项 / 地址 / 引用
```

**不含 `分节符`。** 逐值写入探测同样确认：`分节符`、`分节`、`分段`、`段落`、`标题`、`说明`、
`描述`、`小标题`、`分组`、`富文本`、`评分`、`矩阵`、`排序`、`文件`、`SECTION`、`SECTION_TYPE`、
`section`、`分组标题` 共 18 个候选**全部**被拒。

同一次探测里放了**对照组**：`文本`/`单选`/`数字`/`图片`/`地址`/`引用`/`多选`/`时间日期`/`选项`
全部接受 —— **对照组通过，所以「全拒」是真的，不是探测坏了**。
（这正是「报告缺陷前必须先证明测量手段本身有效」那条教训。）

老工程也用 `'分节符'` 这个值（`index.vue` L313 / L697 / L818），所以**值本身没错**，
是本部署的枚举没开这一项。因此：

- 演示问卷**不含分节符**；
- `mapper` 的 `section` 分支只能靠**伪造字段**的用例覆盖（见「三、已验证事项」题型清单）；
- 生产环境若配置了分节符，本工程的渲染逻辑仍然适用。

### 10.2 探测留下的脏数据与教训

首次探测（未加对照组）创建了 0 道题，但**第二次带对照组的探测创建了 9 道 `__probe__ *` 题**，
清理没成功 —— 两个原因叠加：

1. `srvdaq_item_cfg_delete` 是 **`condition` 形式**，不是 `data` 形式；
   用 `data: [{id}]` 会报 `6666 调用删除服务[...]，必须携带条件`。
   正确写法：

   ```text
   [ { serviceName: 'srvdaq_item_cfg_delete',
       condition: [ { colName: 'id', ruleType: 'in', value: '1834,1826,...' } ] } ]
   ```

2. 我把探测输出 `Select-Object -First 14` **截断了**，清理那几行（含失败信息）根本没看到。

教训：**截断输出会把失败藏起来**。清理/删除类操作必须完整看输出。
9 道探测题与那次失败留下的空活动均已删除（`删后剩余题目：0 道` / `活动剩余：0 条`）。
